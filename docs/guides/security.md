# Security

RAG Evaluator is designed for local and self-hosted evaluation workflows. The open
source edition does not include built-in user authentication, so production security
depends on how you deploy it.

## Default Security Model

By default:

- The API is unauthenticated.
- The frontend assumes direct access to the backend.
- Uploaded documents are stored on disk.
- Indexes and artifacts are stored on disk or in local vector/graph services.
- LLM provider keys are read from environment variables.

This is appropriate for local development. It is not appropriate for a public or shared
deployment without additional controls.

## Production Requirements

Before exposing the platform:

- Put it behind TLS.
- Add authentication at a reverse proxy, VPN, private network, or API gateway.
- Restrict direct access to PostgreSQL, Qdrant, and Neo4j.
- Store secrets in a secret manager.
- Use PostgreSQL instead of SQLite.
- Back up the database and `storage/`.
- Review document sensitivity before upload.
- Define retention rules for uploaded documents, indexes, and artifacts.

## Authentication Options

Recommended approaches:

| Approach | Use case |
| --- | --- |
| Reverse proxy basic auth | Small private deployments. |
| OAuth2/OIDC proxy | Team deployments with SSO. |
| Cloud identity proxy | Cloud-hosted internal tools. |
| VPN/private network | Internal experimentation environments. |

Example nginx pattern:

```nginx
server {
    listen 443 ssl;
    server_name rag-eval.example.com;

    auth_basic "RAG Evaluator";
    auth_basic_user_file /etc/nginx/.htpasswd;

    location / {
        proxy_pass http://frontend:3000;
    }

    location /api/ {
        proxy_pass http://backend:8000;
    }
}
```

## Secrets

Sensitive values include:

- `OPENAI_API_KEY`
- `OPENROUTER_API_KEY`
- `ANTHROPIC_API_KEY`
- `DATABASE_URL`
- `DB_PASSWORD`
- `NEO4J_PASSWORD`

Rules:

- Never commit `.env` files.
- Use different keys for development and production.
- Rotate provider keys regularly.
- Avoid printing settings objects in shared logs unless secrets are redacted.
- Use Docker/Kubernetes/cloud secrets for deployments.

## Document And Artifact Security

Uploaded documents can contain confidential information. The platform stores source
documents, derived chunks, retrieval traces, generated answers, and raw metric data.

Before uploading sensitive data:

- Confirm the deployment is private.
- Confirm the selected LLM provider is allowed to process the data.
- Remove or anonymize PII where possible.
- Review retention requirements.
- Back up and delete storage according to your policy.

`STORAGE_PATH` contains:

```text
documents/
indexes/
artifacts/
reports/
logs/
```

Treat it as sensitive.

## RLM-RAG Security Modes

RLM-RAG's large-corpus agent mode executes Python generated by the orchestrator model;
the small-corpus simple-context fallback does not. Neither generated-code security mode
is a hardened sandbox, so run agent-mode RLM-RAG only in a least-privilege, disposable
environment and do not expose credentials or unrelated host files to the process.

| Mode | Current behavior |
| --- | --- |
| `lite` | Executes generated code in the application process with persistent variables. The configured REPL timeout is not enforced in this mode. Use only for trusted local experimentation. |
| `full` | Runs each block in a subprocess that can be terminated on timeout. The current subprocess does not expose the normal filesystem/worker tools, does not restore variables between blocks, and does not wire in the defined injection wrapper. Treat it as experimental, not as complete isolation. |

Application path checks and model instructions do not replace container or OS sandboxing.
For RLM-RAG experiments, remove unnecessary network access, mounts, environment secrets,
and service-account permissions. Prefer a non-code-executing RAG strategy for untrusted
or multi-tenant corpora.

See [RLM-RAG: indexing and retrieval internals](../../src/rag_evaluator/rag_implementations/rlm_rag/RLM_RAG.md#6-security-status-and-limitations)
for the implementation-level threat and limitation analysis.

## Network Security

Expose only the frontend/reverse proxy to users. Keep these services private:

| Service | Port |
| --- | --- |
| Backend | `8000` |
| PostgreSQL | `5432` |
| Qdrant | `6333`, `6334` |
| Neo4j | `7474`, `7687` |

The backend needs outbound HTTPS access to configured LLM providers unless you use a
local provider such as Ollama.

## Backups

Back up:

- PostgreSQL database.
- `STORAGE_PATH`.
- Qdrant data if using local Qdrant.
- Neo4j data if using local Neo4j.

Test restore procedures before relying on backups for production.

## Incident Response

If a provider key leaks:

1. Revoke the key immediately.
2. Generate a new key.
3. Update deployment secrets.
4. Review logs for suspicious usage.
5. Audit where the key was stored or printed.

If documents leak:

1. Isolate the deployment.
2. Preserve logs for investigation.
3. Identify affected documents, indexes, artifacts, and reports.
4. Rotate credentials that may have been exposed.
5. Delete affected generated storage if policy requires it.
